# Issue writeback protocol — 기존 연구 맥락과 실험 기록 보호

사용자가 **명시적으로** "GitHub 이슈에 반영", "등록", "업데이트" 등을 요청했을 때만 적용. 분석 요청을 곧바로 repository mutation 허가로 해석하지 말라.

1. 연결된 GitHub 도구가 있으면 해당 커넥터로 **현재 저장소·해당 이슈·최신 HEAD·최근 코멘트**를 우선 조회. issue 번호와 저장소가 확인되지 않으면 추측하지 말라. 외부 웹 페이지를 GitHub connector write action의 대체재로 사용하지 말라.
2. 이미 진행 중인 관련 이슈를 우선 찾아 **연구 설계(#6형), 상태 학습(#7형), 실험 무결성(#8형)** 역할로 분류. 숫자는 PHP2Shell의 역사적 예시일 뿐 일반 저장소에서 가정 금지. 중복이 생기면 기존 이슈 보강이 우선.
3. 최신 커밋에서 이미 해결된 문제를 새 P0 미해결로 다시 넣지 말라. `RESOLVED (code)`, `REPORTED rerun`, `UNVERIFIED live`, `OPEN hypothesis`처럼 **상태를 분리**하라.
4. 이슈 본문을 수정할 땐 원문을 먼저 읽어 백업/비교하고, 기존 사전등록·실험 결과·내역을 **보존**하라. 별도 날짜/검토 HEAD가 붙은 추가 섹션을 사용하며 바뀐 정의는 새 버전으로 표기하라. 과거 실험의 실패는 `INVALID/SUPERSEDED` 별도 기록으로 보존.
5. 각 지적에는 **확인된 증거(파일/커밋/로그), 왜 문제가 되는지, 재현 또는 반증할 최소 테스트, 우선순위, 수용 기준, 결과에 따라 Go/No-Go**를 명시하라. 단순 권고만 있는 장황한 이슈를 피하라.
6. 같은 문제가 여러 이슈에 걸칠 때는 **단일 책임 이슈에 상세 실행 계약**, 다른 이슈에는 의존성과 핵심 증상/결정만 넣어 중복 개발을 줄여라.
7. 이슈 변경/생성이 성공한 후 **반영된 실제 URL·번호**를 제공. API가 성공하지 않았다면 게시 완료로 주장하지 말라. 커밋/실험 재실행은 별도 사용자 요청 없이는 하지 말라.

## 추가 섹션 최소 형식

~~~markdown
## [날짜] 6관점 교차 검토 보완 (검토 HEAD [sha])

**판정:** Research Go / Scheduler No-Go / Needs evidence ...
**증거 상태:** CODE_VERIFIED / REPORTED_RESULT / DERIVED / HYPOTHESIS / UNKNOWN

### 확인 사실·이미 수정된 내용
- ... [commit/file/line]

### 미해결 위험과 가정
- ... [원인 → 영향; 범위]

### 최소 반증 실험
- [ ] 양성 대조 ...
- [ ] 음성 대조 ...
- [ ] 독립 관측/재생 ...

### 수용 기준과 중단 기준
- PASS ... / FAIL ...

**의존:** [관련 이슈]
~~~

## 예시: PHP2Shell에서 배운 구체적 주의

- scheduler 설정이 invariant라는 문자열이어도 실제 corpus가 비어 **OFF 경로**로 실행될 수 있다. batch green이면 모두 검증됐다고 말하지 말라.
- `invariant`의 보너스가 0번 발동한 올바른 재실행은 알고리즘 경로 테스트이지 보너스 성능 실험이 아니다.
- "+1" 보너스의 비감쇠는 **정적 수학적 위험**이며, 실제 탐색 고착 여부는 별도 실험으로 관찰해야 한다.
- 최소 구별 실험에서 **원본 요청 인수/환경을 복원하지 못하면** 같음/다름이 아니라 invalid.
